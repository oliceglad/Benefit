# Аудит фронтенда по ТЗ ФСП

Дата: 10.10.2026. Основание: «ФСП спец. трек ТЗ-1.pdf», страницы 2–5, 7–8;
актуальные маршруты и компоненты frontend, существующие серверные контракты.
Backend и инфраструктура в этой итерации не менялись.

## Вывод

**В текущем интерфейсе работодатель не может отбирать кандидатов по достижениям
ФСП.** Нет банка кандидатов, фильтра достижений, карточек достижений и перехода
из подборки к персональному приглашению. Это подтверждает замечание пользователя
именно о фронтенде. Утверждение «в проекте вообще ничего нет» было бы неверным:
серверные модели, поиск и ранжирование уже содержат данные ФСП.

Главная незавершённая часть ТЗ шире фильтра ФСП: обратный рекрутинг
«потребность работодателя → категории и подходящие кандидаты → приглашение
с зарплатой → решение кандидата». В ТЗ это смысловой центр продукта и основной
критерий (35% оценки, стр. 8). Публикация вакансий и самостоятельные отклики
помечены как необязательные для MVP (стр. 4); реализованные вакансии и чат
полезны, но не закрывают основной сценарий.

## Приоритеты оставшейся работы

P0 — необходим для демонстрации главной механики; P1 — обязательная часть
интерфейса, которую следует завершить после неё. Это предложенный порядок работ.

| Приоритет | Требование ТЗ | Текущее состояние frontend | Следующая реализация |
|---|---|---|---|
| P0 | Банк кандидатов по специализации, грейду, категории, стеку и подтверждённым достижениям ФСП | Экрана и навигации нет | Каталог, фильтры в URL, сортировка, подтверждённый грейд и карточки достижений; корректное состояние без истории ФСП |
| P0 | Потребность работодателя и объяснимый подбор категорий/кандидатов | Создаются вакансии; формы потребности и подборки нет | Потребность со стеком, грейдом и описанием команды; серверные рекомендации и причины соответствия; уточнение запроса с сохранением условий |
| P0 | Работодатель первым приглашает кандидата, указывает предложение и зарплатную вилку в рублях | Чат есть; интерфейса создания, входящих/отправленных приглашений и принятия/отказа нет | Приглашение из карточки кандидата, необязательная связь с вакансией, статусы обеих ролей, открытие контактов и переход к чату после серверного подтверждения |
| P1 | Привязка идентификатора ФСП и работа с достижениями | В предпочтениях есть только видимость ФСП и счётчик для уже связанного профиля | Привязка, обновление и подробности достижений; состояния «не связан», «нет истории», «ошибка»; подтверждение берётся из API |
| P1 | Профиль компании: описание, отрасль, контакты | Минимальная настройка перед первой вакансией без контактов; полный профиль остался DEV-экспериментом | Рабочий экран просмотра и изменения компании с контактами |
| P1 | Для опубликованной вакансии и приглашения обязательна вилка «от–до», RUB | Редактор вакансии разрешает пустые суммы и произвольный трёхбуквенный код валюты; отдельной проверки перед публикацией нет | Проверка готовности перед публикацией; черновик может оставаться незаполненным; приглашения сразу требуют корректную вилку |

Анкета, платформенное тестирование, результат, история и ограничения повторной
попытки уже представлены у кандидата. Их не нужно заменять новым тестом; результат
нужно включить в работодателю видимую категорию и подборку. Подтверждённые
сведения не должны редактироваться работодателем или кандидатом вручную.

## Что по ФСП уже существует

- `src/features/candidate-profile/ui/preferences-form.tsx`: сохранение
  `privacy.show_fsp_achievements`; при `profile.fsp.linked` отображается связь
  и количество достижений. Подробного списка, кнопки привязки и синхронизации нет.
- В маршрутах `src/app/router.tsx` и навигации кабинета отсутствуют банк
  кандидатов, потребности, рекомендации и приглашения.
- `GET /api/v1/talent/candidates`: `has_fsp` — наличие подтверждённых достижений,
  `sort=fsp`, специализация, грейды и статус подтверждения. Контракт проверен
  также в OpenAPI работающего локального gateway. Сортировка `fsp` сейчас
  использует количество достижений, затем активность; это не полноценная
  сортировка по ценности каждого спортивного результата.
- `GET /api/v1/employers/needs/{id}/matches`: категории и кандидаты с оценкой,
  причинами соответствия и недостающими навыками. В существующем серверном
  скоринге ФСП уже даёт отдельный вклад. Экран потребности и рекомендаций его
  пока не использует.
- Контракты привязки: `POST /api/v1/auth/oauth/{provider}/link` и
  `POST /api/v1/candidates/me/fsp/sync`. Поля достижения включают мероприятие,
  дисциплину, уровень, результат/место, команду, дату и ссылку.

Наличие контрактов проверено по исходникам; качество выдачи, реальные внешние
учётные записи ФСП и полный цикл синхронизации этим аудитом не проверялись.
Фильтры конкретного мероприятия, дисциплины или призового места публичным
контрактом поиска не объявлены. Для обязательного MVP ТЗ прямо требует фильтр
наличия подтверждённых достижений; детализацию следует согласовать отдельно.

ТЗ не предоставляет реальный API ФСП и разрешает собственный синтетический
набор данных (стр. 3). Поэтому внешний провайдер не должен блокировать
демонстрацию механики. Синтетические сведения нужно явно обозначать; отсутствие
истории ФСП не должно мешать пользоваться платформой.

## Существующие контракты для следующей frontend-итерации

| Сценарий | Контракт |
|---|---|
| Каталог кандидатов | `/api/v1/talent/candidates` |
| Создание/изменение потребности | `/api/v1/employers/needs`, `/api/v1/employers/needs/{id}` |
| Объяснимый подбор | `/api/v1/employers/needs/{id}/matches` |
| Создание и просмотр приглашения | `/api/v1/invitations`, `/api/v1/invitations/{id}` |
| Входящие/отправленные | `/api/v1/invitations/incoming`, `/api/v1/invitations/sent` |
| Решение и отзыв | `/api/v1/invitations/{id}/accept`, `/decline`, `/withdraw` |
| Полный профиль компании | `/api/v1/employers/company` |

Новые клиенты следует получать существующим генератором Orval и подключать
через общий cookie/CSRF-транспорт. Отсутствующие данные или операции передаются
backend-разработчику; фронтенд не подменяет успешный серверный результат.

## Рекомендуемый следующий объём

1. Банк кандидатов с фильтром ФСП, грейдом/стеком и подробностями достижений.
2. Потребность → подборка с причинами → персональное приглашение с зарплатой.
3. Входящие приглашения кандидата, принятие/отказ, статусы и переход к чату.
4. Привязка ФСП, полный профиль компании и проверка зарплаты перед публикацией.

Отдельный список всех откликов, обработка входящих откликов работодателем,
регулярные задания и дальнейшее развитие пайплайнов — после основной механики:
первые сценарии и задания в ТЗ необязательны для MVP, а граф найма сам по себе
не заменяет подбор. Сохранение пайплайнов на сервер пока ожидает контракт
backend-команды. Мобильная версия в ТЗ также необязательна для MVP.

## Проверка этой итерации

Изменён внешний вид графа и раскрытие описания внутри этапа. Успешны
`pnpm build` (включает TypeScript), `pnpm lint` и короткая desktop-проверка
раскрытия/закрытия мышью и клавиатурой. Автотесты и мобильная проверка
не запускались по ранее принятому объёму. Наличие перечисленных пробелов
означает, что весь обязательный frontend ТЗ ещё не завершён.
