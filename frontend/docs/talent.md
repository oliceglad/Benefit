## Поведение

Работодатель открывает «Кандидаты» → `/talent`. Кандидат к этому экрану не
допускается. Выдача использует `GET /api/v1/talent/candidates` из существующего
matching-service, без демонстрационной подмены данных.

Фильтры: ключевые слова, специализация, несколько грейдов, подтверждение тестом,
наличие доступных подтверждённых достижений ФСП, стек со всеми/любыми навыками,
город, формат работы, минимальный опыт и активность. Отдельно можно включить
кандидатов, которые не ищут работу. Кнопка применяет условия целиком.
Категории из ответа API позволяют сузить выдачу по специализации/грейду/статусу.

Сортировки соответствуют API, размер страницы — 12. Условия, сортировка,
страница и раскрытый кандидат хранятся в URL. Раскрытие карточки не сбрасывает
несохранённые поля фильтра и не вызывает новый запрос. После перезагрузки
восстанавливаются поиск и карточка. Профили не сохраняются в localStorage.

Карточка показывает категорию, статус подтверждения грейда, тест и результат
при их наличии, объявленные навыки, ожидания и активность. Достижения ФСП
раскрывают мероприятие, дисциплину, уровень, результат, место, команду, дату
и HTTP(S)-ссылку, если поля предоставлены сервером. Контакты не запрашиваются.
Loading, отсутствие результатов, ошибка с повтором и лимит запросов используют
существующие компоненты и транспорт.

## Семантика и ограничения

- `has_fsp` относится к доступным данным с учётом настроек видимости.
  Отсутствие видимых достижений не доказывает отсутствие истории участия.
- `sort=fsp` сортирует по числу достижений, затем активности, а не по ценности
  призового места. Фильтров конкретного мероприятия/дисциплины в этом API нет.
- Статус грейда поступает с сервера. Обычные навыки из профиля не выдаются за
  подтверждённые тестом; новый результат тестирования не создаётся.
- Снимок OpenAPI получен от работающего локального gateway. Репозиторий main
  содержит также новое поле `verified_skills`, которого этот снимок ещё не
  объявляет. В этой итерации UI не зависит от него. Обновление Docker-образов
  и серверного контракта остаётся работой backend-команды.
- Персональное приглашение — следующий этап P0. Текущая итерация ещё не
  замыкает обратный рекрутинг целиком.

## Потребности в существующем разделе

Новые экраны и маршруты не добавлены. В `/talent` выбор «Кого подбираем»
переключает существующий банк и подбор по сохранённой потребности.
«Создать потребность» и «Изменить условия» открывают редактор прямо в разделе.
Если компания ещё не создана, используется существующая первичная форма
компании. Потребность сохраняется через API и не публикуется как вакансия.

Редактор сохраняет название, команду, специализацию, грейд, обязательные и
желательные навыки, бюджет, город, форматы и количество сотрудников. В
«Точности подбора» доступны подтверждённый грейд, допустимое отклонение,
минимальный опыт и строгие условия стека, бюджета и формата. При изменении
сохраняются все серверные настройки; пустые необязательные значения очищаются.
Новые потребности используют RUB; валюта ранее созданной не меняется молча.
Валидация проверяет диапазоны, вилку и наличие значений для строгих условий.
Изменённая форма защищена от случайного выхода; повторная отправка блокируется.
Закрытие и возобновление потребности используют серверный статус.

Подборка показывает серверные категории, оценку из 100, причины и предупреждения.
В той же раскрываемой карточке доступны совпавшие, близкие и недостающие навыки,
а также вклад компонентов оценки, включая ФСП, если он возвращён сервером.
Фронтенд не пересчитывает баллы и не выдаёт их за вероятность найма.
Причины исключения и подсказки расширения выдачи также приходят с сервера;
подсказка ведёт в редактор и не применяет выдуманный набор изменений.

Идентификатор потребности, страница, скрытие уже контактированных кандидатов и
раскрытая карточка сохраняются в URL. Кэш разделён по аккаунту и потребности;
изменение требований инвалидирует результаты и обновляет условия по ответу API.
Неструктурированный ответ работодателя проверяется схемой перед отображением.

API `needs/{id}/matches` принимает только пагинацию и `hide_contacted`, поэтому
ручные фильтры банка, включая `has_fsp`, не применяются к этой подборке.
Они остаются в URL для возвращения к банку и не отправляются в неподдерживаемый
endpoint. Для строгого фильтра ФСП вместе с подбором по потребности требуется
расширение серверного контракта. Серверный вклад ФСП в оценку уже отображается.

## Проверка

В видимом desktop-браузере выполнен штатный вход ранее созданного smoke-работодателя.
Локальный API вернул три опубликованных синтетических профиля. Сочетание
`Python, PostgreSQL` и подтверждённого грейда оставило один профиль. Карточка
раскрывается мышью и Enter, показывает серверный результат 94,1% и Senior.
После перезагрузки сохранились условия, сортировка и раскрытие.

Фильтр наличия ФСП вернул 0 профилей: проверено корректное пустое состояние.
В живой базе нет доступных достижений, поэтому заполненный список результатов
ФСП ещё не проверен на живых данных. Отсутствие истории отображается корректно.
Пагинация реализована, но на трёх профилях переход на вторую страницу недоступен.

У завершённого профиля кандидата с 69% общего заполнения кнопки жюри скрыты:
источник решения — серверный `onboarding_completed`, а не необязательные поля.
Остались ручные согласия и публикация, прохождение тестов не менялось.

Предыдущая итерация: сборка с TypeScript, lint и 21 целевой тест в трёх файлах.

Проверка потребности: в desktop-браузере через живой gateway создана синтетическая
«Тестовая команда · Python Backend». Требование подтверждённого грейда оставило
один профиль; два исключения и подсказка расширения пришли с сервера. После
добавления Kafka условия сохранились, оценка пересчиталась с 80 до 68 из 100,
а карточка показала Kafka как недостающий навык. Проверены защита изменённой
формы, закрытие/возобновление потребности, фильтр уже контактированных и
восстановление потребности/карточки после перезагрузки. Для первичной настройки
компании добавлен возврат в банк с защитой несохранённых данных. Ветка без
компании в этой проверке не проходилась: smoke-работодатель уже имеет компанию.
Файлы и согласия не изменялись, приглашения не отправлялись.

Успешны build/TypeScript, lint и пять целевых тестов модели потребности и
параметров поиска. Полный регресс и мобильная проверка отложены по запросу.
