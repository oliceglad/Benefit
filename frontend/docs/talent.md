## Поведение

Работодатель открывает «Кандидаты» → `/talent`. Кандидат к этому экрану не
допускается. Выдача использует `GET /api/v1/talent/candidates` из существующего
matching-service, без демонстрационной подмены данных.

Фильтры: ключевые слова, специализация, несколько грейдов, подтверждение тестом,
наличие доступных подтверждённых достижений ФСП, стек со всеми/любыми навыками,
город, формат работы, минимальный опыт и активность. Отдельно можно включить
кандидатов, которые не ищут работу. Кнопка применяет условия целиком.
Категории из ответа API позволяют сузить выдачу по специализации/грейду/статусу.

Сортировки соответствуют API, размер страницы — 12. Условия, сортировка,
страница и раскрытый кандидат хранятся в URL. Раскрытие карточки не сбрасывает
несохранённые поля фильтра и не вызывает новый запрос. После перезагрузки
восстанавливаются поиск и карточка. Профили не сохраняются в localStorage.

Карточка показывает категорию, статус подтверждения грейда, тест и результат
при их наличии, объявленные навыки, ожидания и активность. Достижения ФСП
раскрывают мероприятие, дисциплину, уровень, результат, место, команду, дату
и HTTP(S)-ссылку, если поля предоставлены сервером. Контакты не запрашиваются.
Loading, отсутствие результатов, ошибка с повтором и лимит запросов используют
существующие компоненты и транспорт.

## Семантика и ограничения

- `has_fsp` относится к доступным данным с учётом настроек видимости.
  Отсутствие видимых достижений не доказывает отсутствие истории участия.
- `sort=fsp` сортирует по числу достижений, затем активности, а не по ценности
  призового места. Фильтров конкретного мероприятия/дисциплины в этом API нет.
- Статус грейда поступает с сервера. Обычные навыки из профиля не выдаются за
  подтверждённые тестом; новый результат тестирования не создаётся.
- Снимок OpenAPI получен от работающего локального gateway. Репозиторий main
  содержит также новое поле `verified_skills`, которого этот снимок ещё не
  объявляет. В этой итерации UI не зависит от него. Обновление Docker-образов
  и серверного контракта остаётся работой backend-команды.
- Потребность, объяснение соответствия запросу и персональное приглашение —
  следующие этапы P0. Эта итерация не замыкает обратный рекрутинг целиком.

## Проверка

В видимом desktop-браузере выполнен штатный вход ранее созданного smoke-работодателя.
Локальный API вернул три опубликованных синтетических профиля. Сочетание
`Python, PostgreSQL` и подтверждённого грейда оставило один профиль. Карточка
раскрывается мышью и Enter, показывает серверный результат 94,1% и Senior.
После перезагрузки сохранились условия, сортировка и раскрытие.

Фильтр наличия ФСП вернул 0 профилей: проверено корректное пустое состояние.
В живой базе нет доступных достижений, поэтому заполненный список результатов
ФСП ещё не проверен на живых данных. Отсутствие истории отображается корректно.
Пагинация реализована, но на трёх профилях переход на вторую страницу недоступен.

У завершённого профиля кандидата с 69% общего заполнения кнопки жюри скрыты:
источник решения — серверный `onboarding_completed`, а не необязательные поля.
Остались ручные согласия и публикация, прохождение тестов не менялось.

Успешны сборка с TypeScript, lint и 21 целевой тест в трёх файлах. Полный регресс
и мобильная проверка отложены согласно объёму хакатона.
