# Вакансии и конструктор пайплайнов

Итерация от 10.10.2026. Изменения относятся только к `frontend/`.

Уточнение 11.10 после включения main `898f1c3`: в backend уже существует
`/api/v1/hiring` для процессов найма, этапов, интервью и офферов. Frontend
пока не подключён к этим операциям. Они не предоставляют сохранение произвольных
шаблонов конструктора; заметки ниже об ожидании контракта относятся к шаблонам,
а не к отсутствию серверной модели найма целиком.

## Экраны и доступ

| Маршрут | Доступ | Поведение |
|---|---|---|
| `/vacancies` | Кандидат | Опубликованные вакансии, поиск, фильтры, страницы по 12 записей |
| `/vacancies` | Работодатель | Собственные вакансии с серверными статусами, фильтрация и страницы на клиенте |
| `/vacancies/$vacancyId` | Кандидат | Условия, навыки, сопроводительное письмо и отклик |
| `/vacancies/$vacancyId` | Работодатель | Просмотр собственной вакансии и переход в конструктор |
| `/vacancies/new` | Работодатель | Создание серверного черновика; при отсутствии компании — её обязательные сведения |
| `/vacancies/$vacancyId/edit` | Работодатель | Редактирование полной собственной вакансии |
| `/pipelines` | Работодатель | Конструктор и локальные черновики |
| `/preview/pipelines` | Только DEV | Тот же конструктор; авторизованный аккаунт может выбрать опубликованную вакансию из каталога для локального просмотра |

Регистрация теперь предлагает две существующие серверные роли: кандидат и
работодатель. Cookie/CSRF-транспорт сохранён. После входа работодатель попадает
на вакансии, кандидат — в профиль. Сервер остаётся источником роли и прав доступа.

## Подключённые существующие операции

| Операция | Назначение |
|---|---|
| `GET /api/v1/vacancies` | Каталог опубликованных вакансий |
| `GET /api/v1/vacancies/{id}` | Карточка для кандидата |
| `GET /api/v1/employers/vacancies` | Собственные вакансии работодателя и варианты привязки черновика |
| `GET /api/v1/employers/vacancies/{id}` | Собственная карточка, включая неопубликованные вакансии |
| `POST /api/v1/employers/vacancies` | Создание черновика |
| `PUT /api/v1/employers/vacancies/{id}` | Сохранение всех редактируемых полей, с сохранением существующего `need_id` |
| `PATCH /api/v1/employers/vacancies/{id}` | Публикация, возврат в черновик и закрытие |
| `GET /api/v1/employers/company` | Компания для создания вакансии |
| `PUT /api/v1/employers/company` | Первичная настройка компании, только если она ещё отсутствует |
| `GET /api/v1/applications` | Собственные отклики кандидата |
| `POST /api/v1/applications` | Отклик с необязательным сопроводительным письмом |

Поиск `q` работает по названию и описанию. Дополнительные фильтры: грейд,
формат, город, нижняя граница зарплаты. Фильтры и offset находятся в URL;
обновление страницы и Back/Forward сохраняют выбранные условия.

Отклик подтверждается только после успешного ответа API. Перед отправкой
кандидат видит уведомление об открытии контактов работодателю. Уже активный
отклик отображается вместо повторной отправки. Новые запросы используют общий
транспорт, отмену и таймаут 15 секунд. OpenAPI-снимки и клиенты Orval находятся
в `openapi/` и `src/shared/api/generated/`.

## Создание, редактирование и публикация

Форма состоит из роли, условий и описания. Поддержаны все существующие
специализации и грейды, необязательные формат/занятость/город, валютный код,
зарплатная вилка и до 30 навыков. Клиент повторяет ограничения API: название
200 символов, описание 8000, город 100, навык 64, целые суммы 0–100 000 000,
нижняя граница не выше верхней. Описание остаётся обычным текстом без HTML.

Работодатель видит обновляемую карточку и полный предпросмотр. Создание всегда
сохраняет черновик; публикация выполняется отдельной подтверждаемой операцией
на странице вакансии. PUT уже опубликованной вакансии сохраняет статус,
изменения становятся видны кандидатам; об этом есть подсказка в редакторе.
Снятие с публикации переводит в draft, закрытие — в closed. Сервер поддерживает
повторную публикацию обоих статусов. После успеха обновляются данные карточки
и запросы каталога/списка; ошибка не показывается как успешное сохранение.

Редактор загружает полные данные, поэтому описание и существующая связь с
потребностью не теряются. Несохранённые изменения защищены при навигации и
закрытии страницы. Сервер не предоставляет версии/ETag для конфликтов двух
редакторов: применяется существующее поведение PUT.

При `company_not_found` новый работодатель сначала вводит название, отрасль
из серверного enum и описание компании. Это минимальная зависимость вакансии,
а не замена отдельного профиля компании. Перед созданием повторяется GET, чтобы
не затереть уже созданную в другой вкладке компанию; атомарного create-only
контракта у текущего PUT нет.

Из Zite Applicant Tracking взяты компоновочные решения формы и компактных
строк вакансий. MIT, commit `efde414cb971e075b27325fafb05577bd8f1f9f1`;
источники в `component-sources.yaml`, уведомление в `THIRD_PARTY_NOTICES.md`.
Зависимости Zite, донорские данные и неподдерживаемые сервером поля не включены.

## Конструктор

По запросу пользователя предложен стартовый набор из 10 этапов:
«Новый кандидат», «Первичный отбор», «HR-интервью», «Техническое интервью»,
«Тестовое задание», «Встреча с командой», «Финальное интервью», «Оффер»,
«Оформление», «Выход на работу».

Можно добавлять этапы из библиотеки, менять названия и описания, переставлять
кнопками вверх/вниз, убирать этапы и смотреть итоговую последовательность.
Повторное использование одного типа создаёт новый этап с собственным UUID.
Платформенное тестирование кандидата эти этапы не запускают и не изменяют.

Сохранение выполняется явно в localStorage, с отдельным ключом для аккаунта.
Предпросмотр использует ключ `design-preview` и не смешивается с черновиками
работодателя. В хранилище лежит только конфигурация этапов и необязательный ID
вакансии. Кандидаты, оценки и контакты туда не записываются. Смена маршрута
с несохранёнными изменениями предлагает сохранить черновик или остаться.

**Допущения этой frontend-итерации:** от 1 до 16 этапов, до 30 локальных
черновиков; название пайплайна до 120 символов, этапа до 80, описание до 500.
Это технические ограничения клиента, а не утверждённые серверные правила.

## Граф в вакансии — уточнение дизайна

Кандидат видит все этапы прямо в карточке вакансии до отклика. Предпросмотр
конструктора использует тот же компонент. Представление стилизовано под Git-граф:
компактные строки, узлы, изгибы ответвлений и объединения с основной линией.
Нажатие этапа раскрывает его описание прямо под строкой, повторное — закрывает.
Одновременно раскрыт один этап; правой карточки подробностей нет. Скругление
строк и описаний повторяет части знака Benefit. Клавиатура использует обычные
кнопки и существующий Radix Collapsible. Это чтение, а не изменение прогресса.

Используются общие токены интерфейса: основной маршрут — `--primary`,
HR/командные встречи — более светлый вариант того же синего, технические
этапы — `--destructive`. Белая поверхность, границы и текст соответствуют
остальным карточкам. Отдельная фиолетовая палитра, верхняя цветная полоска,
декоративные иконки и английские подписи веток убраны. Цвет обозначает группу
этапа, не успешность или отказ. Порядок остаётся
порядком конструктора, сверху вниз; ветки не задают параллельность или обязательность.

Для локальной демонстрации в DEV:

1. Выбрать вакансию в конструкторе. В кабинете работодателя доступны собственные
   вакансии; в `/preview/pipelines` — до 100 опубликованных вакансий из каталога
   при существующей сессии. Поля вакансии не меняются.
2. Нажать «Показать в вакансии». Действие сохраняет черновик и отдельный снимок
   конфигурации под ключом конкретной вакансии в этом браузере.
3. Открыть карточку вакансии. Она показывает этот снимок с отметкой
   «Локальный предпросмотр»; обновления из другой вкладки подхватываются автоматически.

Остальные черновики аккаунтов не перебираются и не открываются кандидату.
Если снимка нет, DEV показывает явно обозначенный пример из семи этапов.
В production локальные снимки и демонстрационный маршрут отключены: до появления
контракта этапов отображается «Компания пока не предоставила маршрут отбора».
Это локальный просмотр дизайна, а не публикация пайплайна через API.

`shared/ui/branch-graph` — компонент без API и бизнес-логики. Отображение типов
этапов на ветки принадлежит `features/pipelines`. Страница вакансии и пайплайн
собираются вместе в `app/pages/vacancy-page.tsx`, без импорта приватных модулей
одной фичи в другую. Общее хранилище снимков содержит только конфигурацию этапов.

## Задача для backend-разработчика

Для сохранения в аккаунт нужен согласованный контракт CRUD пайплайнов:

- ID и владелец пайплайна, название, необязательная привязка к собственной вакансии.
- Упорядоченные этапы со стабильными ID, типом, редактируемыми названием и описанием.
- Проверка владельца и привязки на сервере, ограничения и ошибки в общем формате.
- Версия либо дата изменения для обработки одновременного редактирования.
- Отдельный контракт движения кандидатов, если он понадобится следующей итерации.
- В выдаче вакансии кандидат должен получать всю опубликованную конфигурацию
  маршрута. Личный прогресс кандидата нужен отдельным контрактом и не выводится
  из общих статусов отклика `new/viewed/invited`.

Адреса новых операций намеренно не назначены до согласования с backend-командой.
Фронтенд не вызывает API сохранения пайплайнов. Настройка последовательности
пока не изменяет серверные статусы отклика и не перемещает кандидатов автоматически.

Чат работодателя с кандидатом реализован в отдельной frontend-фиче;
контракты и ограничения описаны в [chat.md](chat.md). Английские бейджи
имён веток убраны из графа по уточнению дизайна.

Актуальная сверка с обязательными требованиями ТЗ и приоритеты обратного
рекрутинга записаны в [frontend-tz-audit.md](frontend-tz-audit.md).

## Проверка и локальное окружение

TypeScript, lint и production-сборка проверены. В браузере открыты каталог и
карточка из живого API; в конструкторе добавлен и переставлен этап, сохранён
локальный черновик и открыт предпросмотр. После уточнения дизайна проверены
выбор узла графа и привязка шести настроенных этапов к вакансии: кандидатская
вкладка получила тот же маршрут без перезагрузки.

В итерации создания вакансий выполнен вход обеих ролей, создание синтетического
черновика, редактирование зарплаты, публикация, возврат в draft, закрытие и
повторная публикация. Соискатель увидел новую вакансию в каталоге и полные
сохранённые условия. Проверены валидация вилки, защита несохранённых данных
и перенаправление кандидата с `/vacancies/new` в каталог. Сценарий первой
настройки компании в этой проверке не запускался: у тестового работодателя
компания уже была. Отправка нового отклика, полный регресс и мобильная проверка
не выполнялись. Новые тесты не добавлялись по запросу пользователя.

До уточнения границы «только фронт» в локальном Docker уже была применена
экспериментальная миграция `0003` с таблицей `hiring_pipelines` и скопирован
экспериментальный API. Все соответствующие изменения исходников backend
удалены из рабочей копии. Уже запущенное локальное окружение далее не менялось;
данный frontend эти экспериментальные операции не использует. Ранее сделанные
изменения окончаний строк `entrypoint.sh` также не относятся к этой итерации.
